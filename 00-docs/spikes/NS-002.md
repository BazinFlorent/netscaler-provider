# NS-002 — Module HCL direct, CRUD et idempotence

Date de préparation : 6 octobre 2026.  
Statut : **NON EXÉCUTÉ — protocole et trame de compte rendu préparés**.

## Objectif

Prouver qu’un module HCL exécuté directement par OpenTofu peut créer et gérer un load balancer HTTP NetScaler CPX, transmettre du trafic aux backends A/B, puis converger vers un plan sans changement.

Chaîne testée : **OpenTofu local → provider Terraform citrix/citrixadc → NITRO → CPX → backends A/B**.

Crossplane est présent dans le lab, mais aucune MR Workspace ni XR n’intervient dans ce spike. Cette étape permet d’isoler les limites du provider ADC, du module et du réseau avant l’accostage Crossplane.

## Questions à résoudre

1. Les ressources virtual server, service group, membres et bindings choisies fonctionnent-elles avec notre CPX ?
2. Quel adressage du virtual server permet de recevoir le trafic sur le port CPX 8080 publié en WSL 18080 ?
3. OpenTofu crée-t-il les dépendances dans le bon ordre et relève-t-il correctement leurs identités ?
4. Le LB transmet-il vingt requêtes réussies, avec les deux backends observés ?
5. Le second plan est-il vide après stabilisation ?
6. Comment évoluent méthode de répartition, membres et port : update en place, remplacement, erreur ou absence de synchronisation ?
7. La suppression du module nettoie-t-elle les objets créés sans modifier les backends ni les objets hors périmètre ?

## Préparation de la session

Depuis la racine du dépôt :

```bash
tofu version
docker compose -f 01-lab/cpx/compose.yaml up -d
docker compose -f 01-lab/cpx/compose.yaml ps

curl -fsS http://localhost:18081
curl -fsS http://localhost:18082

BACKEND_A_IP="$(docker inspect poc-netscaler-backend-a \
  --format '{{with index .NetworkSettings.Networks "kind"}}{{.IPAddress}}{{end}}')"
BACKEND_B_IP="$(docker inspect poc-netscaler-backend-b \
  --format '{{with index .NetworkSettings.Networks "kind"}}{{.IPAddress}}{{end}}')"

printf 'Backend A : %s:8080\nBackend B : %s:8080\n' \
  "$BACKEND_A_IP" "$BACKEND_B_IP"
```

Attendu : CPX et les backends Up, réponses A/B correctes et adresses non vides. Attendre le démarrage CPX avant les appels NITRO. Refaire le contrôle NITRO de NS-001 si le lab a été redémarré ou recréé.

## Protocole et critères de validation

### 1. Lire le schéma et écrire le module minimal

Écrire un module avec un virtual server HTTP, un service group, deux membres A/B et leur binding. Choisir une seule façon de gérer chaque binding : aucun cumul de bloc inline et de ressource dédiée pour le même objet.

Après configuration de l’authentification et du state, depuis le répertoire du module :

```bash
tofu fmt -check
tofu init
tofu validate
tofu providers
```

Consulter le schéma avec `tofu providers schema -json` et conserver, si nécessaire, sa sortie dans un fichier local ignoré par Git. Relever les paramètres requis, valeurs normalisées, règles d’exclusion et informations disponibles sur le cycle de vie. Le schéma seul ne suffit pas à prédire tous les remplacements : vérifier les plans, la documentation et, au besoin, le code du provider.

**Attendu :** module valide, version du provider connue, périmètre et dépendances explicites.

### 2. Création et inventaire ADC

```bash
tofu plan -detailed-exitcode
```

Inspecter le plan avant `tofu apply` : seules les créations `poc-ns002-*` attendues doivent apparaître. Relever objets et IDs dans le state et l’inventaire NITRO après apply. Ne pas déposer un state brut dans Git ou le CR.

**Attendu :** apply terminé, aucun objet étranger modifié, ressources et bindings présents. Compléter les commandes NITRO exactes une fois les types sélectionnés.

### 3. Trafic HTTP via le LB

Depuis la WSL, vingt requêtes, chacune dans un processus curl distinct :

```bash
for request in $(seq 1 20); do
  printf '%02d : ' "$request"
  curl -fsS --connect-timeout 5 --max-time 10 \
    http://localhost:18080/ || break
done
```

**Attendu :** vingt requêtes réussies, réponses A et B toutes deux observées. Ne pas exiger une alternance stricte sans qualifier l’algorithme ; désactiver la persistance de session pour ce test. Si la boucle s’arrête sur une erreur, le critère des vingt succès n’est pas satisfait.

### 4. Idempotence après stabilisation

```bash
tofu plan -detailed-exitcode
```

Codes : **0 = aucun changement ; 1 = erreur ; 2 = changements proposés**. Relever immédiatement le code avec `echo "$?"` avant une autre commande.

**Attendu :** code 0, sans modification du HCL ni de l’ADC entre apply et plan. Une sortie normalisée ou un binding toujours modifié doit être expliqué, pas masqué d’emblée par ignore_changes.

### 5. Modifications, une variable à la fois

| Cas | Protocole | Preuve attendue |
|---|---|---|
| Algorithme LB | Modifier la méthode puis plan/apply, trafic et nouveau plan | Update/remplacement identifié, méthode appliquée, convergence |
| Membres | Retirer B, vérifier uniquement A, puis rétablir B | Binding correct, A préservé, A/B retrouvés, plan vide |
| Port du virtual server | Préparer un mapping Docker vers le port alternatif, modifier le port, inspecter plan puis appliquer | Distinguer remplacement ADC et problème de publication Docker ; endpoint fonctionnel sur le nouveau port |

Pour chaque cas : sauvegarder une preuve expurgée du plan, relever les IDs avant/après, la durée et le résultat HTTP. Ne pas ajouter un second binding avec un autre propriétaire pour contourner une erreur du premier.

### 6. Suppression nominale du LB jetable

Après collecte des preuves, inspecter `tofu plan -destroy`, puis exécuter `tofu destroy` avec confirmation si le plan correspond uniquement au module NS-002.

**Attendu :** bindings et objets propriétaires supprimés ; aucun objet `poc-ns002-*` orphelin ; backends A/B toujours fonctionnels en accès direct. La suppression avec pannes, finalizers et objets partagés sera approfondie dans NS-010.

Ne pas supprimer le state ni le lab CPX avant confirmation de la suppression des objets ADC. Si des objets sont conservés pour la suite, le documenter et conserver leur state : le sous-test de suppression reste alors NON EXÉCUTÉ.

## Pièges et workarounds à qualifier

| Piège | Limite / contournement à tester |
|---|---|
| Virtual server créé mais inaccessible | Vérifier adressage CPX, port interne et mapping Docker, bindings et santé des membres |
| Ressource ou attribut non compatible CPX | Réduire le module aux champs qualifiés ; consigner la différence à vérifier sur VPX |
| Plan qui modifie toujours un binding | Vérifier propriété unique, normalisation et défauts du provider ; corriger avant Workspace |
| Changement de port remplaçant le virtual server | Relever l’interruption et restreindre le contrat produit si nécessaire |
| Attribut non relu par le provider | Le déclarer hors garantie de réconciliation ; tester la dérive dans NS-006 |
| ignore_changes proposé comme raccourci | Dernier recours documenté : le champ exclu n’est plus réconcilié normalement |
| Échec partiel / objet créé hors state | Inventorier state et ADC avant retry ; aucune suppression de state suivie d’un apply aveugle |
| Secrets dans variables, plan ou state | Exclure fichiers sensibles de Git, expurger les preuves ; Sensitive ne chiffre pas le state |
| Apply réussi pris pour une preuve HTTP | Vérifier les vingt requêtes : succès de provisioning et service fonctionnel sont deux résultats distincts |

Aucun workaround n’est encore validé dans NS-002.
