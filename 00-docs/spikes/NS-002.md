# NS-002 — Module HCL direct, CRUD et idempotence

Date de préparation : 6 octobre 2026.  
Statut : **TERMINÉ — PASS AVEC LIMITES DOCUMENTÉES ; remplacement du port corrigé dans le HCL**.

## Objectif

Prouver qu’un module HCL exécuté directement par OpenTofu peut créer et gérer un load balancer HTTP NetScaler CPX, transmettre du trafic aux backends A/B, puis converger vers un plan sans changement.

Chaîne testée : **OpenTofu local → provider Terraform citrix/citrixadc → NITRO → CPX → backends A/B**.

Crossplane est présent dans le lab, mais aucune MR Workspace ni XR n’intervient dans ce spike. Cette étape permet d’isoler les limites du provider ADC, du module et du réseau avant l’accostage Crossplane.

### Fichiers du module et rôle de chacun

| Fichier | Contenu / rôle |
|---|---|
| `versions.tf` | Contraintes de version OpenTofu, source/version du provider et déclaration du backend local |
| `provider.tf` | Instance du provider citrixadc ; credentials et endpoint lus dans l’environnement |
| `variables.tf` | Contrat d’entrée : VIP, port, méthode et map des backends |
| `main.tf` | Graphe des ressources ADC et leurs références |
| `.terraform.lock.hcl` | Versions et checksums des dépendances générés par init ; à versionner |
| `.terraform/` | Installation locale et métadonnées du backend ; à ignorer |

Le fichier utilisé s’appelle `provider.tf` (singulier). Le nom `providers.tf` serait aussi valide : OpenTofu charge tous les fichiers `.tf` du répertoire. Le nom n’affecte pas la sémantique ; ne pas conserver deux copies déclarant le même provider.

### Initialisation du module et state isolé

Depuis la racine du dépôt :

```bash
mkdir -p 01-lab/hcl/netscaler .local/ns002

cat > 01-lab/hcl/netscaler/versions.tf <<'EOF'
terraform {
  required_version = ">= 1.13.0, < 1.14.0"

  required_providers {
    citrixadc = {
      source  = "registry.terraform.io/citrix/citrixadc"
      version = "= 2.3.0"
    }
  }

  backend "local" {}
}
EOF

cat > 01-lab/hcl/netscaler/provider.tf <<'EOF'
provider "citrixadc" {}
EOF

NS002_STATE_PATH="$(pwd)/.local/ns002/terraform.tfstate"

tofu -chdir=01-lab/hcl/netscaler init \
  -backend-config="path=${NS002_STATE_PATH}"

tofu -chdir=01-lab/hcl/netscaler validate
tofu -chdir=01-lab/hcl/netscaler providers

tofu -chdir=01-lab/hcl/netscaler providers schema -json \
  > .local/ns002/provider-schema.json

jq -r '
  .provider_schemas[]
  .resource_schemas
  | keys[]
  | select(
      . == "citrixadc_lbvserver"
      or . == "citrixadc_servicegroup"
      or . == "citrixadc_servicegroup_servicegroupmember_binding"
      or . == "citrixadc_lbvserver_servicegroup_binding"
    )
' .local/ns002/provider-schema.json
```

**Observé :** les quatre types ci-dessus sont présents dans le schéma du provider installé. Les sorties complètes de init/validate n’ont pas été partagées ; le plan réussi ensuite confirme que le module est exploitable pour la planification.

Le bloc HCL garde le nom `terraform` même sous OpenTofu. `required_version` contraint le moteur CLI, pas le provider. `required_providers` fixe la dépendance ADC.

Le backend local est configuré séparément à l’initialisation. Le chemin absolu pointe vers la racine du dépôt malgré `-chdir`, qui place l’exécution dans le module. Le state suit les identités des objets créés ; il n’est ni le code HCL ni la configuration persistante propre à CPX. Il sera alimenté lors de l’apply ; le premier plan ne prouve pas la création d’un state contenant des objets.

`.local/` et `.terraform/` doivent être ignorés dans Git, contrairement à `.terraform.lock.hcl`. Le fichier de schéma est conservé dans `.local/ns002/`. Ne pas modifier ni supprimer le state à l’aveugle ; si le dépôt est déplacé, le chemin absolu mémorisé dans le backend nécessite une reconfiguration/migration explicite conservant le state existant.

### Définir les variables

```bash
cat > 01-lab/hcl/netscaler/variables.tf <<'EOF'
variable "vip" {
  description = "Adresse Docker de CPX utilisée comme VIP dans le lab."
  type        = string
}

variable "lb_port" {
  description = "Port interne du virtual server."
  type        = number
  default     = 8080
}

variable "lb_method" {
  description = "Méthode de répartition."
  type        = string
  default     = "ROUNDROBIN"
}

variable "backends" {
  description = "Membres du pool, identifiés par une clé logique stable."
  type = map(object({
    ip   = string
    port = number
  }))
}
EOF
```

Les clés logiques `a` et `b` servent d’identité HCL aux membres ; elles ne sont pas remplacées par leurs IP dans for_each. Un changement d’IP peut néanmoins entraîner un remplacement du binding : à qualifier par le plan.

### Décrire les cinq ressources ADC

```bash
cat > 01-lab/hcl/netscaler/main.tf <<'EOF'
resource "citrixadc_lbvserver" "http" {
  name            = "poc-ns002-http"
  servicetype     = "HTTP"
  ipv46           = var.vip
  port            = var.lb_port
  lbmethod        = var.lb_method
  persistencetype = "NONE"
}

resource "citrixadc_servicegroup" "http" {
  servicegroupname = "poc-ns002-pool"
  servicetype      = "HTTP"
}

resource "citrixadc_servicegroup_servicegroupmember_binding" "backend" {
  for_each = var.backends

  servicegroupname = citrixadc_servicegroup.http.servicegroupname
  ip               = each.value.ip
  port             = each.value.port
}

resource "citrixadc_lbvserver_servicegroup_binding" "http" {
  name             = citrixadc_lbvserver.http.name
  servicegroupname = citrixadc_servicegroup.http.servicegroupname

  lifecycle {
    replace_triggered_by = [citrixadc_lbvserver.http.port]
  }
}
EOF
```

Le bloc lifecycle ci-dessus représente la version corrigée finale. Il était absent de la version initiale ; la section G conserve le résultat sans correction.

Un virtual server, un service group, deux bindings de membres et un binding virtual server/pool donnent **cinq instances de ressources**, pour quatre types. Les références HCL expriment les dépendances. Le binding virtual server/pool dépend de ces deux objets, pas de la présence préalable de tous les membres : le provisioning peut traverser une période temporairement non fonctionnelle.

La persistance de session est désactivée pour observer A/B. Aucun binding inline ne duplique une ressource dédiée. Le futur chemin de trafic est WSL:18080 → IP CPX:8080 → pool → backends:8080.

## Protocole et critères de validation

### 1. Lire le schéma et écrire le module minimal

Écrire un module avec un virtual server HTTP, un service group, deux membres A/B et leur binding. Choisir une seule façon de gérer chaque binding : aucun cumul de bloc inline et de ressource dédiée pour le même objet.

Après configuration de l’authentification et du state, depuis le répertoire du module :

```bash
tofu fmt -check
tofu providers
tofu validate
```

Le backend doit d’abord être initialisé selon la section « Initialisation du module et state isolé » ; ne pas remplacer cette étape par un init utilisant implicitement le state par défaut du répertoire.

Consulter le schéma avec `tofu providers schema -json` et conserver, si nécessaire, sa sortie dans un fichier local ignoré par Git. Relever les paramètres requis, valeurs normalisées, règles d’exclusion et informations disponibles sur le cycle de vie. Le schéma seul ne suffit pas à prédire tous les remplacements : vérifier les plans, la documentation et, au besoin, le code du provider.

**Attendu :** module valide, version du provider connue, périmètre et dépendances explicites.

### 2. Création et inventaire ADC

```bash
tofu plan -detailed-exitcode
```

Inspecter le plan avant `tofu apply` : seules les créations `poc-ns002-*` attendues doivent apparaître. Relever objets et IDs dans le state et l’inventaire NITRO après apply. Ne pas déposer un state brut dans Git ou le CR.

**Attendu :** apply terminé, aucun objet étranger modifié, ressources et bindings présents. Compléter les commandes NITRO exactes une fois les types sélectionnés.

### 3. Trafic HTTP via le LB

Depuis la WSL, vingt requêtes, chacune dans un processus curl distinct :

```bash
for request in $(seq 1 20); do
  printf '%02d : ' "$request"
  curl -fsS --connect-timeout 5 --max-time 10 \
    http://localhost:18080/ || break
done
```

**Attendu :** vingt requêtes réussies, réponses A et B toutes deux observées. Ne pas exiger une alternance stricte sans qualifier l’algorithme ; désactiver la persistance de session pour ce test. Si la boucle s’arrête sur une erreur, le critère des vingt succès n’est pas satisfait.

### 4. Idempotence après stabilisation

```bash
tofu plan -detailed-exitcode
```

Codes : **0 = aucun changement ; 1 = erreur ; 2 = changements proposés**. Relever immédiatement le code avec `echo "$?"` avant une autre commande.

**Attendu :** code 0, sans modification du HCL ni de l’ADC entre apply et plan. Une sortie normalisée ou un binding toujours modifié doit être expliqué, pas masqué d’emblée par ignore_changes.

### 5. Modifications, une variable à la fois

| Cas | Protocole | Preuve attendue |
|---|---|---|
| Algorithme LB | Modifier la méthode puis plan/apply, trafic et nouveau plan | Update/remplacement identifié, méthode appliquée, convergence |
| Membres | Retirer B, vérifier uniquement A, puis rétablir B | Binding correct, A préservé, A/B retrouvés, plan vide |
| Port du virtual server | Utiliser un pod vers IP CPX:8081, modifier le port, inspecter plan puis appliquer | Distinguer remplacement ADC et problème de publication Docker ; endpoint fonctionnel sur le nouveau port |

Pour chaque cas : sauvegarder une preuve expurgée du plan, relever les IDs avant/après, la durée et le résultat HTTP. Ne pas ajouter un second binding avec un autre propriétaire pour contourner une erreur du premier.

### 6. Suppression nominale du LB jetable

Après collecte des preuves, inspecter `tofu plan -destroy`, puis exécuter `tofu destroy` avec confirmation si le plan correspond uniquement au module NS-002.

**Attendu :** bindings et objets propriétaires supprimés ; aucun objet `poc-ns002-*` orphelin ; backends A/B toujours fonctionnels en accès direct. La suppression avec pannes, finalizers et objets partagés sera approfondie dans NS-010.

Ne pas supprimer le state ni le lab CPX avant confirmation de la suppression des objets ADC. Si des objets sont conservés pour la suite, le documenter et conserver leur state : le sous-test de suppression reste alors NON EXÉCUTÉ.

## Pièges et workarounds à qualifier

| Piège | Limite / contournement à tester |
|---|---|
| Virtual server créé mais inaccessible | Vérifier adressage CPX, port interne et mapping Docker, bindings et santé des membres |
| Ressource ou attribut non compatible CPX | Réduire le module aux champs qualifiés ; consigner la différence à vérifier sur VPX |
| Plan qui modifie toujours un binding | Vérifier propriété unique, normalisation et défauts du provider ; corriger avant Workspace |
| Changement de port remplaçant le virtual server | Binding perdu sans déclencheur explicite ; replace_triggered_by sur le port validé au retour 8080 ; interruption non mesurée |
| Attribut non relu par le provider | Le déclarer hors garantie de réconciliation ; tester la dérive dans NS-006 |
| ignore_changes proposé comme raccourci | Dernier recours documenté : le champ exclu n’est plus réconcilié normalement |
| Échec partiel / objet créé hors state | Inventorier state et ADC avant retry ; aucune suppression de state suivie d’un apply aveugle |
| Secrets dans variables, plan ou state | Exclure fichiers sensibles de Git, expurger les preuves ; Sensitive ne chiffre pas le state |
| Apply réussi pris pour une preuve HTTP | Vérifier les vingt requêtes : succès de provisioning et service fonctionnel sont deux résultats distincts |

Workaround validé : remplacement explicite du binding sur changement du port (section G). Il ne garantit pas une modification sans interruption et ne couvre pas les autres attributs pouvant forcer un remplacement.
