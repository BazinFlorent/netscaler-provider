# NS-004 — Accostage Crossplane par MR Workspace

Date de préparation : 7 octobre 2026.  
Statut : **PRÉPARÉ — commandes d’installation fournies ; résultat du provider à confirmer**.

## Objectif

Faire piloter le module HCL NetScaler qualifié par une Managed Resource Workspace Crossplane : créer un LB, transmettre du trafic, modifier les entrées déclaratives, puis retrouver les mêmes objets après redémarrage du provider grâce au backend externe.

Chaîne cible : **MR Workspace → provider OpenTofu Crossplane → moteur OpenTofu → provider Terraform citrixadc → NITRO → CPX → backends A/B**.

Ce spike ajoute le contrôleur Crossplane à la chaîne validée en CLI. Il n’introduit pas encore la XRD métier LoadBalancer ni une Composition produit. La reprise du pod provider complète le volet différé de NS-003.

## Deux providers, deux rôles

| Composant | Fonction |
|---|---|
| Provider OpenTofu Crossplane | Réconcilier la MR Workspace et lancer les opérations du moteur HCL |
| Provider Terraform citrixadc | Lire/écrire les objets ADC via NITRO |

Le package OpenTofu ne crée pas quatre MR NetScaler : l’unité de contrôle reste une MR Workspace contenant le module de cinq ressources HCL. Les états Crossplane seront comparés au state et au trafic, sans assimiler Ready à un succès HTTP.

## Choix de préparation

- Package épinglé : xpkg.upbound.io/upbound/provider-opentofu:v1.1.8. Ne pas remplacer par latest pendant le spike.
- Manifests : `01-lab/crossplane/ns004/`.
- Premier module : source Inline proposée, pour isoler le contrôle du module des problèmes de récupération Git. Le HCL sera dérivé du module validé ; source distante et packaging pourront être qualifiés ensuite.
- Noms ADC proposés : poc-ns004-http / poc-ns004-pool ; port 8080 pour réutiliser la publication WSL 18080.
- Identité MR/external-name et suffixe backend : à figer après inspection du comportement de la release ; utiliser une identité NS-004 distincte des states A/B historiques.
- Authentification backend depuis pod : accès in-cluster à préparer ; pas de copie du kubeconfig WSL dans les manifests.
- Endpoint NITRO depuis pod : IP Docker courante de CPX:9080 ; ne pas utiliser localhost:19080.
- Outputs envisagés : nom et endpoint du LB ; aucun mot de passe en output.

Le moteur dans le conteneur peut différer du tofu local 1.13.1. Ne pas retirer la contrainte required_version à l’aveugle : relever d’abord le moteur et décider explicitement d’un runtime compatible ou d’une qualification adaptée.

## Étape 1 — Installer le provider

Commandes déjà fournies le 7 octobre ; aucune sortie d’installation complète partagée à ce stade.

Depuis la racine du dépôt :

```bash
mkdir -p 01-lab/crossplane/ns004

cat > 01-lab/crossplane/ns004/provider.yaml <<'YAML'
apiVersion: pkg.crossplane.io/v1
kind: Provider
metadata:
  name: provider-opentofu
spec:
  package: xpkg.upbound.io/upbound/provider-opentofu:v1.1.8
YAML

kubectl --context kind-netscaler-provider apply \
  -f 01-lab/crossplane/ns004/provider.yaml
kubectl --context kind-netscaler-provider get providers.pkg.crossplane.io
kubectl --context kind-netscaler-provider get pods -n crossplane-system
kubectl --context kind-netscaler-provider get crd | grep opentofu
```

Attendu après installation : provider INSTALLED=True et HEALTHY=True, pod disponible, CRD OpenTofu présentes. Ne pas créer la MR avant ces contrôles. Si l’installation est bloquée, relever les conditions et événements :

```bash
kubectl --context kind-netscaler-provider describe \
  provider.pkg.crossplane.io/provider-opentofu
kubectl --context kind-netscaler-provider get providerrevisions.pkg.crossplane.io
kubectl --context kind-netscaler-provider get events \
  -n crossplane-system --sort-by=.metadata.creationTimestamp
```

La commande initialement proposée utilisait rg (ripgrep), absent de la WSL. L’utilisateur indique qu’il l’installe. Cette version du protocole utilise grep pour ce filtre simple : l’absence de rg est un problème d’outil local, pas une preuve d’échec du package.

## Étape 2 — Inventorier l’API et le runtime avant configuration

Afficher les scopes et versions des CRD sans supposer que la version d’API du README suffit :

```bash
kubectl --context kind-netscaler-provider get crd -o json \
  | jq -r '.items[] | select(.spec.group | contains("opentofu")) |
    [.metadata.name, .spec.scope,
     ([.spec.versions[] | select(.served) | .name] | join(","))] | @tsv'

kubectl --context kind-netscaler-provider get deployments \
  -n crossplane-system -o wide
kubectl --context kind-netscaler-provider get pods \
  -n crossplane-system -o wide
```

À partir des noms réellement observés : lire les CRD avec kubectl explain/get, identifier le pod/container du provider, relever image/digest et exécuter tofu version si le binaire est accessible. Les commandes adaptées seront ajoutées une fois les ressources identifiées.

Relever les champs source/module, vars/varmap/env, références Secrets, providerConfigRef, outputs, connection secret, deletionPolicy et éventuelles managementPolicies. Un champ présent dans une API commune ne prouve pas que toutes ses valeurs sont mises en œuvre par le provider.

## Limites à surveiller

- Répertoire /tf du pod éphémère : backend externe requis pour une reprise sans perte de state.
- Noms : metadata.name, external-name, workspace CLI et suffixe de backend peuvent sélectionner des identités différentes. Consigner leur correspondance réelle ; pas de renommage opportuniste.
- Ready ne prouve pas la santé HTTP ni la présence de deux backends actifs.
- Poll de dérive et réaction à une modification de spec sont deux mécanismes à mesurer séparément. Le README du provider annonce un poll par défaut de dix minutes ; relever la configuration réelle.
- Timeout d’exécution et lock après interruption : cas approfondis en NS-008.
- Correction de remplacement du port de NS-002 à conserver ; aucune garantie de continuité pendant remplacement.
- Backend dans kind : survie au pod à tester, survie au reset cluster non acquise.
- MR Workspace gère le module entier ; granularité et objets partagés seront approfondis en NS-005.
