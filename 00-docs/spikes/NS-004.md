# NS-004 — Accostage Crossplane par MR Workspace

Date de préparation : 7 octobre 2026. Mise à jour : 9 octobre 2026.

**Statut : EN COURS — création, trafic A/B, state externe et configuration B seul validés ; rétablissement de A, reprise du provider et suppression restant à tester.**

Ce document est destiné à `00-docs/spikes/NS-004.md`. Les commandes s’exécutent depuis la racine du dépôt WSL `netscaler-provider`. Les résultats observés sont distingués des résultats attendus des prochains tests.

## 1. Objectif et périmètre

Faire piloter les ressources NetScaler par un **MR (Managed Resource) Workspace Crossplane** : créer un LB, transmettre du trafic, modifier les membres déclarés, retrouver les mêmes ressources après redémarrage du provider, puis les supprimer par suppression du MR.

Chaîne testée : **MR Workspace → provider OpenTofu Crossplane → moteur OpenTofu → provider Terraform CitrixADC → API NITRO → CPX → backends**.

Le Workspace représente un module HCL entier, ici cinq instances : un virtual server, un service group, deux bindings de membres et un binding entre virtual server et service group. Le backend Kubernetes conserve le state et son verrou ; il ne crée pas les objets ADC. Ceux-ci sont gérés via NITRO par CitrixADC.

Le MR est autonome : nous modifions directement son manifeste, ce qui est un usage normal de Crossplane. Aucune XRD produit ni Composition n’intervient dans ce spike. Lorsqu’une Composition générera ce MR, les modifications devront être portées dans le XR ou la Composition pour éviter leur écrasement.

Le test de reprise du provider complète le volet différé de NS-003. Aucun CLI OpenTofu local n’est nécessaire pour les opérations de création/modification/suppression de NS-004.

## 4. Préparer namespace, credentials et droits — VALIDÉ

Le pod utilise `http://<IP Docker CPX>:9080`, pas le port WSL `localhost:19080`.

```bash
kubectl --context kind-netscaler-provider create namespace netscaler-ns004 \
  --dry-run=client -o yaml \
  | kubectl --context kind-netscaler-provider apply -f -

CPX_IP="$(docker inspect poc-netscaler-cpx \
  --format '{{with index .NetworkSettings.Networks "kind"}}{{.IPAddress}}{{end}}')"
CPX_PASSWORD="$(docker exec poc-netscaler-cpx \
  cat /var/deviceinfo/random_id)"

printf '%s' "$CPX_PASSWORD" \
  | kubectl --context kind-netscaler-provider \
      create secret generic ns004-nitro \
      -n netscaler-ns004 \
      --from-file=NS_PASSWORD=/dev/stdin \
      --dry-run=client -o yaml \
  | kubectl --context kind-netscaler-provider apply -f -
```

`random_id` contient le mot de passe initial du lab. Si le mot de passe nsroot a été changé manuellement, employer celui en vigueur. Ne pas afficher la variable ou activer `set -x`.

Le compte de service doit pouvoir lire le Secret NITRO et gérer les Secrets/Leases du backend. Adapter son nom à la sortie de la section 3.2 :

```bash
NS004_PROVIDER_SA="provider-opentofu-97b0250cf8b1"
NS004_PROVIDER_ID="system:serviceaccount:crossplane-system:${NS004_PROVIDER_SA}"

kubectl --context kind-netscaler-provider auth can-i get secret/ns004-nitro \
  -n netscaler-ns004 --as="$NS004_PROVIDER_ID"

for resource in secrets leases.coordination.k8s.io; do
  for verb in get list create update patch delete; do
    printf '%s %s : ' "$verb" "$resource"
    kubectl --context kind-netscaler-provider auth can-i \
      "$verb" "$resource" \
      -n netscaler-state --as="$NS004_PROVIDER_ID"
  done
done
```

**Résultat observé :** `yes` pour la lecture du Secret et les douze contrôles du backend. Aucun RBAC supplémentaire n’a été créé pour ce test. Cela démontre l’accès requis, pas une isolation de moindre privilège : les droits effectifs peuvent dépasser ceux contrôlés.

## 6. Déclarer le MR Workspace et créer le LB — VALIDÉ

### 6.1. Manifeste initial complet et génération des IP

`workspace.yaml` est **le manifeste du MR Workspace**. Les IP sont découvertes à la génération du fichier, puis deviennent des valeurs fixes. Cette génération complète prépare un rejeu initial avec A et B ; ne pas la relancer pendant le scénario B seul, car elle rétablirait A.

```bash
CPX_IP="$(docker inspect poc-netscaler-cpx \
  --format '{{with index .NetworkSettings.Networks "kind"}}{{.IPAddress}}{{end}}')"
BACKEND_A_IP="$(docker inspect poc-netscaler-backend-a \
  --format '{{with index .NetworkSettings.Networks "kind"}}{{.IPAddress}}{{end}}')"
BACKEND_B_IP="$(docker inspect poc-netscaler-backend-b \
  --format '{{with index .NetworkSettings.Networks "kind"}}{{.IPAddress}}{{end}}')"

cat > 01-lab/crossplane/ns004/workspace.yaml <<EOF
apiVersion: opentofu.m.upbound.io/v1beta1
kind: Workspace
metadata:
  name: ns004-http
  namespace: netscaler-ns004
  annotations:
    crossplane.io/external-name: ns004-http
spec:
  providerConfigRef:
    kind: ProviderConfig
    name: ns004
  forProvider:
    source: Inline
    inlineFormat: HCL
    enableTofuCLILogging: true
    env:
      - name: NS_URL
        value: "http://${CPX_IP}:9080"
      - name: NS_LOGIN
        value: nsroot
      - name: NS_PASSWORD
        secretKeyRef:
          name: ns004-nitro
          key: NS_PASSWORD
    varmap:
      vip: "${CPX_IP}"
      lb_port: 8080
      lb_method: ROUNDROBIN
      backends:
        a:
          ip: "${BACKEND_A_IP}"
          port: 8080
        b:
          ip: "${BACKEND_B_IP}"
          port: 8080
    module: |
      variable "vip" {
        type = string
      }

      variable "lb_port" {
        type = number
      }

      variable "lb_method" {
        type = string
      }

      variable "backends" {
        type = map(object({
          ip   = string
          port = number
        }))
      }

      resource "citrixadc_lbvserver" "http" {
        name            = "poc-ns004-http"
        servicetype     = "HTTP"
        ipv46           = var.vip
        port            = var.lb_port
        lbmethod        = var.lb_method
        persistencetype = "NONE"
      }

      resource "citrixadc_servicegroup" "http" {
        servicegroupname = "poc-ns004-pool"
        servicetype      = "HTTP"
      }

      resource "citrixadc_servicegroup_servicegroupmember_binding" "backend" {
        for_each         = var.backends
        servicegroupname = citrixadc_servicegroup.http.servicegroupname
        ip               = each.value.ip
        port             = each.value.port
      }

      resource "citrixadc_lbvserver_servicegroup_binding" "http" {
        name             = citrixadc_lbvserver.http.name
        servicegroupname = citrixadc_servicegroup.http.servicegroupname

        lifecycle {
          replace_triggered_by = [
            citrixadc_lbvserver.http.port
          ]
        }
      }

      output "lb_name" {
        value = citrixadc_lbvserver.http.name
      }

      output "lb_port" {
        value = citrixadc_lbvserver.http.port
      }
EOF
```

Le ProviderConfig injecte le bloc `terraform` et la configuration du provider ADC ; le module Inline contient les variables, ressources et outputs. `varmap` transporte les entrées ; `env.secretKeyRef` fournit le mot de passe sans l’inscrire dans Git.

La correction `replace_triggered_by` de NS002 est conservée. Elle porte sur le **port** ; elle n’établit pas à elle seule le comportement de remplacement lors d’un changement de VIP.

### 6.2. Appliquer et observer

```bash

  --dry-run=server -f 01-lab/crossplane/ns004/workspace.yaml
kubectl --context kind-netscaler-provider apply \
```

**Résultat observé :** `SYNCED=True`, `READY=False` à 4 secondes, puis `SYNCED=True`, `READY=True` à 6 secondes. Ce délai vient de la sortie watch initiale, pas d’une mesure de performance reproductible.

## 7. Identifier le state et les verrous — VALIDÉ

```bash
kubectl --context kind-netscaler-provider get \
  secrets,leases.coordination.k8s.io -n netscaler-state

kubectl --context kind-netscaler-provider get leases \
  -n netscaler-state \
  -o custom-columns='NAME:.metadata.name,HOLDER:.spec.holderIdentity'
```

| Identité | Secret | Lease |
|---|---|---|
| Workspace OpenTofu initial `default` | `tfstate-default-ns004` | `lock-tfstate-default-ns004` |
| Workspace sélectionné `ns004-http` | `tfstate-ns004-http-ns004` | `lock-tfstate-ns004-http-ns004` |

Le nom du MR et son `crossplane.io/external-name` sont tous deux `ns004-http` ; le suffixe de backend est `ns004`. Les objets NS003 restent présents avec leurs suffixes séparés.

Lire uniquement le résumé des states :

```bash
for secret in tfstate-default-ns004 tfstate-ns004-http-ns004; do
  kubectl --context kind-netscaler-provider get secret "$secret" \
    -n netscaler-state -o json \
    | python3 -c '
import sys, json, base64, gzip
secret = json.load(sys.stdin)
raw = base64.b64decode(secret["data"]["tfstate"])
if raw.startswith(b"\x1f\x8b"):
    raw = gzip.decompress(raw)
state = json.loads(raw)
print(json.dumps({
    "secret": secret["metadata"]["name"],
    "lineage": state.get("lineage"),
    "serial": state.get("serial"),
    "instances": sum(len(r.get("instances", []))
                     for r in state.get("resources", []))
}, indent=2))
'
done
```

**Résultats observés :** zéro instance dans `default`, cinq dans `ns004-http`, détenteurs des quatre Leases NS003/NS004 affichés `<none>` au relevé. Le state vide `default` est compatible avec l’initialisation du backend avant sélection du workspace nommé ; il ne porte pas un second LB. Ne supprimer aucun de ces objets pendant le spike.

Les valeurs lineage/serial NS004 n’ont pas été partagées : elles restent à relever pour la reprise du provider. Le nombre d’instances après retrait de A reste également à mesurer ; quatre sont attendues.

## 8. Retirer A et conserver B — VALIDÉ AVEC REMISE EN ÉTAT RÉSEAU

### 8.1. Modifier le manifeste et vérifier la déclaration

Dans `workspace.yaml`, supprimer uniquement `a` de `spec.forProvider.varmap.backends`, conserver `b` avec son IP actuelle. Ne pas modifier le HCL : `for_each` gère les membres déclarés.

```bash
kubectl --context kind-netscaler-provider apply \
  -f 01-lab/crossplane/ns004/workspace.yaml

kubectl --context kind-netscaler-provider get \
  workspaces.opentofu.m.upbound.io ns004-http \
  -n netscaler-ns004 -o json | jq '{
    backends: .spec.forProvider.varmap.backends,
    conditions: .status.conditions

```

Première tentative : commande lancée depuis `~`, chemin relatif introuvable. Après `cd netscaler-provider`, l’apply répondait `unchanged` car la modification n’avait pas été sauvegardée. Après sauvegarde, `configured` et B seul apparaissait dans la déclaration Kubernetes.

### 8.2. Incident observé : cible arrêtée et IP devenues obsolètes

Le Workspace affichait `SYNCED=False`, `READY=True`. Le message `Synced` indiquait :

```text
observe failed: cannot diff (i.e. plan) tofu configuration
GET http://172.18.0.7:9080/nitro/v1/config/servicegroup_servicegroupmember_binding/poc-ns004-pool
connect: no route to host
```

OpenTofu ne pouvait pas lire l’ADC pour calculer le plan. `READY=True` ne suffisait pas à valider la configuration actuelle. Diagnostic :

```bash
kubectl --context kind-netscaler-provider get \
  workspaces.opentofu.m.upbound.io ns004-http \
  -n netscaler-ns004 -o json | jq '.status.conditions'

docker compose -f 01-lab/cpx/compose.yaml ps

  poc-netscaler-cpx poc-netscaler-backend-a poc-netscaler-backend-b \
  --format '{{.Name}} => {{with index .NetworkSettings.Networks "kind"}}{{.IPAddress}}{{end}}'
```

**Résultat :** aucun service en cours dans `compose ps`, IP affichées `invalid IP`. Le lab a été redémarré avec :

```bash
./01-lab/cpx/launch.sh
```

Après redémarrage, les trois conteneurs étaient Up et les IP avaient changé :

| Conteneur | Avant arrêt | Après reprise du 9 octobre |
