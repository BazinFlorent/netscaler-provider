# NS-003 — Identité, backend et reprise du state

Date de préparation : 7 octobre 2026.  
Statut : **PRÉPARÉ — aucun test NS-003 exécuté**.

## Objectif

Démontrer qu’un nouvel exécuteur retrouve les mêmes ressources NetScaler grâce à un state externalisé, sans recréer les objets ni produire de doublons. Qualifier aussi la séparation de deux identités de state et une restauration maîtrisée.

NS-002 a validé le cycle de vie du module direct ; ses cinq ressources sont maintenant supprimées. Son state local est vide et conservé. Le module corrigé contient replace_triggered_by sur le port pour la liaison vserver/pool.

## Ce que nous testons

Le code HCL décrit les objets souhaités. Le state associe chaque adresse HCL à l’ID réel sur ADC. Le backend stocke ce state hors du répertoire d’exécution. Le verrou protège un state contre des écritures concurrentes ; il ne verrouille pas globalement l’ADC.

Choix proposé pour ce lab : backend Kubernetes, state dans un Secret et verrou via une Lease. Cela survit au remplacement d’un exécuteur tant que le cluster et ses données sont conservés. Ce n’est pas une sauvegarde indépendante de kind et cela ne garantit pas la survie à la suppression du cluster.

| Identité | Valeur proposée pour A | Rôle |
|---|---|---|
| Contexte Kubernetes | kind-netscaler-provider | Cluster hébergeant le backend |
| Namespace | netscaler-state | Périmètre de stockage |
| Workspace CLI OpenTofu | default | Sélection du workspace du backend |
| secret_suffix | ns003-a | Identité stable du state A |
| Secret attendu | tfstate-default-ns003-a | Nom documenté du state ; confirmer l’objet réel |
| Vserver ADC | poc-ns003-a-http | Identité ADC, à paramétrer avant création |
| Service group ADC | poc-ns003-a-pool | Identité du pool, à paramétrer avant création |
| Adresse HCL | citrixadc_lbvserver.http | Adresse dans le module, indépendante du nom ADC |
| ID du provider | À relever après apply | Identité effective relue sur ADC |
| Lineage / serial | À relever par state pull | Identité et révision du state |
| MR Workspace / external-name | Non créé | Correspondance à vérifier en NS-004 |

Un Workspace CLI OpenTofu et une MR Workspace Crossplane sont deux notions différentes. Le lien exact entre le nom/external-name de la MR et le backend sera qualifié avec la release installée en NS-004 ; ne pas le déduire de ce seul test.

## Prérequis

- Lab NS-001 disponible ; CPX et les backends répondent.
- NS-002 clôturé : state list vide, vserver/pool NS-002 absents.
- OpenTofu 1.13.1, provider citrixadc 2.3.0, lockfile conservé.
- Kubeconfig utilisateur accessible ; contexte explicite kind-netscaler-provider.
- Droits de gestion des Secrets et Leases dans le namespace choisi.
- Un seul writer pendant reprise et restauration ; pas encore de contrôleur Crossplane sur ces objets.

Le backend Kubernetes documente une limite de taille liée aux Secrets (1 Mio). Le state peut contenir des données sensibles : ne pas l’afficher intégralement ni le versionner. TLS/RBAC approfondis relèvent de NS-011.

## Étape 1 — Préparer un module distinct et le namespace

Depuis la racine du dépôt :

```bash
./01-lab/cpx/launch.sh
kubectl --context kind-netscaler-provider get nodes

tofu -chdir=01-lab/hcl/netscaler state list
# Attendu à la clôture NS-002 : aucune adresse

mkdir -p 01-lab/hcl/netscaler-state .local/ns003
cp 01-lab/hcl/netscaler/*.tf 01-lab/hcl/netscaler-state/
cp 01-lab/hcl/netscaler/.terraform.lock.hcl \
  01-lab/hcl/netscaler-state/.terraform.lock.hcl

kubectl --context kind-netscaler-provider create namespace netscaler-state \
  --dry-run=client -o yaml \
  | kubectl --context kind-netscaler-provider apply -f -

for resource in secrets leases.coordination.k8s.io; do
  for verb in get list create update patch delete; do
    printf '%s %s : ' "$verb" "$resource"
    kubectl --context kind-netscaler-provider auth can-i \
      "$verb" "$resource" -n netscaler-state
  done
done
```

Cette copie ne transporte ni `.terraform/` ni le state local. Elle permet de conserver le module NS-002 et son rejeu avec backend local. Le répertoire netscaler-state sert aux tests suivants et pourra être adapté pour NS-004. Les commandes cp sont une préparation initiale : ne pas les rejouer après modification, au risque d’écraser cette adaptation.

**Attendu :** lab disponible, state NS-002 vide, nouveau namespace, réponses yes pour les droits contrôlés. Les droits de la session utilisateur ne préjugent pas de ceux du futur ServiceAccount provider.

## Étape 2 — Déclarer le backend Kubernetes

Dans `01-lab/hcl/netscaler-state/versions.tf`, conserver les contraintes de versions et remplacer uniquement `backend "local" {}` par `backend "kubernetes" {}` :

```hcl
terraform {
  required_version = ">= 1.13.0, < 1.14.0"

  required_providers {
    citrixadc = {
      source  = "registry.terraform.io/citrix/citrixadc"
      version = "= 2.3.0"
    }
  }

  backend "kubernetes" {}
}
```

Initialisation depuis WSL :

```bash
tofu -chdir=01-lab/hcl/netscaler-state init \
  -backend-config="namespace=netscaler-state" \
  -backend-config="secret_suffix=ns003-a" \
  -backend-config="config_path=${HOME}/.kube/config" \
  -backend-config="config_context=kind-netscaler-provider"

tofu -chdir=01-lab/hcl/netscaler-state workspace show
tofu -chdir=01-lab/hcl/netscaler-state fmt -check
tofu -chdir=01-lab/hcl/netscaler-state validate
```

Attendu : backend initialisé, workspace default, configuration valide. On initialise une copie neuve avec une nouvelle identité ; aucune migration du state NS-002 vide n’est nécessaire. L’existence d’un Secret à cette étape ne démontre pas qu’il contient des ressources : contrôler après création.

Ne pas appliquer encore : le module copié utilise les noms NS-002. La prochaine étape doit rendre les noms ADC paramétrables et fixer l’identité A avant toute écriture.

## Étapes suivantes — à exécuter progressivement

| Test | Actions prévues | Critère |
|---|---|---|
| Créer A | Paramétrer les noms, exporter credentials/IP A/B, créer les cinq ressources sur port 8080 | Trafic A/B, IDs relevés, plan 0 |
| Externalisation | Relever Secret/Lease sans données, sauvegarder par state pull dans .local/ns003, lire uniquement lineage/serial/IDs | State dans le backend choisi, inventaire attendu |
| Perte du répertoire d’exécution | Préparer un autre répertoire avec seulement code et lockfile ; init sur namespace/suffix/workspace identiques | Mêmes lineage/IDs, plan 0, aucune nouvelle création |
| Isolation B | Même module, suffixe ns003-b, noms ADC B distincts, port différent ; pas de double ownership | States A/B distincts ; B n’adopte pas A ; contrôles ADC séparés |
| Restauration | Sur une identité jetable, writers arrêtés, sauvegarde et état courant vérifiés ; restauration sans force ni suppression aveugle du Secret A | Lineage/serial et IDs cohérents, plan conforme après restauration |
| Reprise du pod provider | Après NS-004, redémarrer le contrôleur puis vérifier state, ADC et trafic | Aucune création inattendue ; validation reportée jusque-là |
| Nettoyage | Détruire chaque périmètre depuis son propre state ; préserver lab et preuves | Aucun objet de test restant, aucun mélange de states |

Le détail des commandes de création, isolation et restauration sera ajouté après validation des étapes précédentes. En particulier, ne pas utiliser state push -force, force-unlock ou supprimer un Secret de state comme procédure normale de reprise. Les erreurs de lock et pertes de backend relèvent de NS-008.

## Preuves à conserver

Pour chaque cas : version/commit, contexte/namespace/suffix/workspace, adresses HCL, IDs ADC, lineage/serial, compteurs du plan et code de retour, réponse HTTP, effet sur l’autre périmètre. Éviter les credentials, le contenu brut des Secrets et le state complet dans le CR.
